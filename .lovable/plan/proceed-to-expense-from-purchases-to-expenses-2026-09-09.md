# Proceed to Expense — from Purchases to Expenses

## What already happens today (verified)

- A purchase becomes an Expense automatically the moment its Payment Status is set to **Paid**. That is how PO-20260724-001 became EXP-00257.
- If a Paid purchase is set back to Pending, its linked expense is removed again.
- Right now 1 of 26 purchases is Paid, so 25 rows are not eligible to be forwarded yet.

Because you chose "only Paid purchases", the new controls do not create a second ledger entry — they make the existing link visible, and give you a confirmation step where you can set the Expense Category and Payment Mode instead of accepting the automatic values.

## What you get

1. **Checkbox column** as the first column, with Select All in the header.
   - A row is selectable only when it is Paid and has no expense yet.
   - Pending rows: checkbox disabled, tooltip "Mark payment as Paid first".
   - Already-forwarded rows: checkbox disabled.
2. **Floating selection banner** at the bottom while rows are selected:
   `3 items selected · Total: ₹XX,XXX` with a **Proceed to Expense** button and a Clear link.
3. **Forward to Expense** button in the Actions column (arrow-up-right icon) next to View/Delete, with the same eligibility rules.
4. **"Forwarded to Expense" badge** on rows that already have a linked expense, showing the expense number (e.g. `EXP-00257`) and linking to that entry on the Expenses page.
5. **Confirmation modal** listing every selected purchase with auto-mapped fields:
   - Title: `PO: {invoice_number} — {supplier_name}`
   - Amount, Date, Vendor/Payee (supplier), Payment Method (from payment mode)
   - Category mapped from Type: Pharmacy / Drug Company → Pharma Charges, Consumables → Clinic consumables, Dental Material Company → Clinical Matierials, anything else → Inventory Purchase
   - Category and Payment Mode are editable per row before submitting.
6. **On confirm**: the expense entries are created (or, where the automatic rule already made one, updated to your chosen category/payment mode), the Purchases list and Expenses list refresh, and a success toast appears with a **View in Expenses** button.

## Duplicate prevention

The link already lives on the expense record (`purchase_id`), so one purchase can only ever show one linked expense; forwarding is blocked and the badge is shown once a link exists. No extra flag column is needed, and no new field is added to Purchases. A database uniqueness rule on that link is also added so a duplicate can never be created by two people acting at the same time.

## Technical notes

- `src/pages/Purchases.tsx` only: selection state, header/row checkboxes, floating banner, Actions button, badge, confirmation dialog, mutation, toast with navigation to `/expenses`.
- Forwarded state comes from a new query on `expenses (id, expense_number, purchase_id)` filtered to the listed purchase ids — same pattern already used in `Expenses.tsx`.
- Eligibility: `payment_status === 'paid' && !forwardedMap[id]`.
- Insert writes `expense_date`, `category`, `subcategory` (supplier_type), `description`, `amount`, `payment_method`, `paid_to`, `receipt_number` (invoice number), `purchase_id`, `receipt_url` (payment proof if present). `expense_number` is generated by the existing rule.
- One migration: `CREATE UNIQUE INDEX expenses_purchase_id_unique ON public.expenses (purchase_id) WHERE purchase_id IS NOT NULL;` (`Expenses.tsx` already handles that error name). No schema change to `purchases`.
- Untouched: the automatic purchase→expense rule itself, delivery/stock logic, payment status logic, permissions, Expenses page behaviour, WhatsApp/dedupe/quota, pipeline stage guard.
